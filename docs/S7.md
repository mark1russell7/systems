# S7 · Simulated environments

This file holds the plan of S7. The status of each item is in [the roadmap](ROADMAP.md#the-items-of-s7). The plan answers [issue 129](https://github.com/mark1russell7/systems/issues/129). It gives each link of the issue an answer, from a read on 2026-11-04.

## The question

S1, S2 and S3 run on one kernel. Each client, server and router of a cell is a container on one runner. That choice gives real Linux TCP at a low cost. It also hides each fact that needs more than one kernel, a real routing protocol or a real disk. S7 asks which of these facts a laboratory can prove, and at which layer.

Two words have different meanings in this plan:

- **To emulate** is to run the real code on false wires. The timers are real, thus a band can hold them.
- **To simulate** is to replace the code with a model. The timers are those of the model, thus a result tells nothing about the real code.

The program needs emulation for a claim about a real system. It can use simulation for scale and for an exact replay.

Each layer is real code, and each one adds what the layer before it cannot prove. A cell goes on the lowest layer that can prove its claim.

## What each part of the stack gains

### The cells

The `Fault` type gets the faults that one kernel cannot give. These are a loss of a route with the carrier up, a power-off, a kernel panic, a step of a clock and a failed disk. The observer stays the same. The prober runs in the kernel of the guest at E4, and it reads the same timers.

`Topology` is a chain of hops. A fabric has more than one path, thus a chain cannot name it. The first slice adds `Topology.fabric`: a fixed lab of four routers, named by its timers. [SYS-92](ROADMAP.md#sys-92--a-topology-as-a-graph) makes the topology a graph when a law must read the paths.

### Chaos and failover

Today a loss of a node is a stopped container or a set of drop rules. A power-off is different: no FIN, no flush and no ordered exit. A kernel panic is different too. Thus E4 tests the claim that each "node loss" cell of S1 and S2 stands for a real loss.

### Timeouts

Each timer band reads HZ from the kernel of the runner. The runner records that we read show HZ 1000. Thus a band has one value of HZ in each run, and the HZ term has no direct test. E4 sets HZ to 100, 250 and 1000 on one cell. The algebra predicts each value before the run. That is a direct test of the jiffy terms in each band.

### Kubernetes

kind and k3d share one kernel, thus a node cannot lose its kernel. k3s on VMs gives the first real loss of a node. It also gives a second distribution, with SQLite or etcd, flannel and its own process model. A cell that holds on the two distributions tests a law. A cell that holds on one tests a distribution.

### Network faults

`tc` and iptables stay the tools for loss, delay and drops. E3 adds the routing protocol that reacts to them. The new question is the order of the detectors: BFD, the BGP hold timer and TCP's own retransmissions.

### Sites

A site at E3 is a group of containers behind routed links with a real delay. Replication then crosses a route, and a route can change or fail. A topology of three sites holds on one runner only while its systems fit in 16 GB.

### The service model

`lint()` gets rules from the new laws. For example, a service behind BGP must withdraw its route before it stops its intake.

### The algebra

`@mark1russell7/machines` gets documents for BGP, BFD and FRR's timers, from pinned source. The ordering law gets terms for route convergence. A kernel document names its version, and a band reads the document of the kernel that the cell boots. Today one document stands for each kernel of the runners.

## How a result stays comparable

The records of S1, S2 and S3 stay valid, and no record changes. These rules hold each new result to them.

1. **Each record names its environment.** A `substrate` block gives the layer, the kernel, HZ, the cloud of the runner, the presence of KVM and the image of the runner. The digest of each image stays in the manifest. A record with no block reads as E1 through an upgrade. Nothing rewrites it.
2. **The name of a cell holds its layer** when the layer is not E1. Two layers do not share a cell name.
3. **Each new layer starts with a bridge.** A set of T01 cells runs on the old layer and on the new layer, in one job, in pairs. The new layer gives no other result until each bridge cell holds.
4. **Each layer measures its own noise.** An A/A pair gives its δ_abs. Nested virtualization can add steal time, thus E4 records it, and a run that is not quiet is void.
5. **A median comes from one environment.** No statistic pools two layers, two kernels or two clouds. The paired comparison comes from `@mark1russell7/rigor-statistics`.
6. **A band does not move with the layer.** A band moves only through a term that a document names, for example HZ. A cell that fails on one layer only is a finding, not a cause to widen a band.
7. **A clock is local.** A time comes from the kernel of its observer. No time subtracts across two kernels with no sync line in the record.
8. **A missing capability is void, not a failure.** A job on a runner with no KVM ends as void, and the rule of one re-dispatch applies.
9. **A time under load keeps its intended send time, and the maximum.** This is the rule of the InfoQ talk.

## The first slice: SYS-77

The first slice proves two things with one small lab. A new layer can repeat an old result, and it can give a result that no old layer can give.

**The lab.** A client and a Redis server of the harness connect through four FRR routers: two leaves and two spines, with eBGP on each link. The `ext-container` kind wires the containers of the harness into the fabric. The prober stays on the client. This fits on one runner.

**The cells.** Each cell has four counted runs, in two labs.

1. **The bridge.** Three cells of T01 run through the fabric, on a route that does not change. They are an idle black hole, an in-flight black hole and a stall of 1 s. The band of E1 must hold, with the same timers.
2. **BGP only.** Spine1 goes silent, with the carrier up. The BGP hold timer of each leaf finds it, and the route moves.
3. **BFD.** The same fault, with BFD on each link.
4. **The control.** A stream of 8 s through the same lab, with no fault.

**The timers.** BGP uses a keepalive of 2 s and a hold of 6 s. BFD uses 240 ms × 3. So a move comes 4 s to 6 s, or 0.48 s to 0.72 s, after the silence, plus the install of the route. At HZ 1000, no firing of the client lands in those intervals. A firing between the two leaf moves is a different case. The target gets the request and its reply dies. Then the recovery follows the ladder of the target. `silencePrediction` stops if a move can reach a firing.

**The settings of the lab.** Graceful restart is off: a helper can keep stale routes after a hold expiry, and the move does not come. Each link has an MTU of 1500, because the default of containerlab, 9500, changes the length of a segment against E1. Each leaf holds one best path, so a move is one change of one route.

**The law.** The first good reply comes at the first retransmission after the later of the two moves. Thus the recovery time is not the detection time. It is a step of the ladder of the RTO. The bands come from the pinned source of FRR before the dispatch, and they do not change after a result.

**The prediction.** The numbers went to the record of predictions before the dispatch, with the bands.

| Claim | Probability |
| --- | --- |
| The lab runs and gives each cell 4 counted runs and no void on the first dispatch | 0.35 |
| Each bridge cell holds the band of E1 | 0.80 |
| The δ_abs of the fabric is at most twice that of E1 | 0.70 |
| BFD moves the routes in less than 4 s in each run | 0.95 |
| Each BFD move is from 0.48 s to 0.80 s | 0.75 |
| Each BGP move is from 4.0 s to 6.1 s | 0.75 |
| The recovery with BFD is in its band | 0.65 |
| The recovery with BGP is in its band | 0.60 |
| The recovery comes at a step of the ladder, not at the move of the route | 0.75 |
| The connection survives each case, with no reset and no error | 0.85 |
| The control has no failed request, no change of a route and no change of a session | 0.90 |
| The naive claim: the recovery time equals the detection time | 0.05 |

**The value.** If the bridge holds, E3 is a valid layer, and each later item in that line can start. If it fails, the failure tells what the fabric adds before any larger cell depends on it.

## The second slice of SYS-87: recovery and delivery

The first slice (systems #470) times the detection and the reconnect of Socket.IO 4.8.4. This slice counts the events that one drop loses or repeats. Each law comes from the pinned source: socket.io 4.8.4, socket.io-adapter 2.5.8, socket.io-client 4.8.4 and engine.io-client 6.6.7.

**The setup.** Each cell uses the subject of the first slice, with a ping each 2 s and a wait of 1 s for its pong. A `stall` of 6 s stops the path, and then the path comes back. The client detects the stall 3 s after the last ping at most. Its first try waits 0.5 s, and its SYN gets through after the stall. Thus each cell has one disconnect and one new connection.

**The facts of the source.**

- Recovery is off at the default. With `connectionStateRecovery`, the default of `maxDisconnectionDuration` is 2 min (the constructor of `Server`, `dist/index.js` of socket.io).
- With recovery on, `emit` of a socket of the server gives each packet to the adapter (`Socket.emit`, `dist/socket.js`). `SessionAwareAdapter.broadcast` keeps each event with no ack and no volatile flag, with an offset (`dist/in-memory-adapter.js` of socket.io-adapter).
- A restore needs the session and the offset of the last event that the client got (`restoreSession`). The session expires `maxDisconnectionDuration` after the server closes the socket (`persistSession`).
- A timer of the adapter fires each 60 s. It removes each event older than `maxDisconnectionDuration`, independent of the sessions (the constructor of `SessionAwareAdapter`).
- The client writes an event into its socket while its ping did not expire. After `pingInterval + pingTimeout` with no ping, it keeps each new event in `sendBuffer`, and it sends them after the reconnect (`Socket.emit` and `emitBuffered`, `build/cjs/socket.js` of socket.io-client, and `_hasPingExpired` of engine.io-client).
- With `retries`, the client sends one event at a time, and it waits for its ack (`_addToQueue`, `_drainQueue`). Each ack timeout counts a failed try. A disconnect also counts one, because `_clearAcks` gives the pending ack an error. The client drops the event at the first failed try past `retries`.
- `retries: 0` turns the queue off, because `emit` reads the option as a boolean. Thus 0 is not one try with no retry.

**The cells.** Each stream sends one numbered event each 100 ms. The receiver writes a line for each event that it gets.

| Cell | Direction | Settings | Law |
| --- | --- | --- | --- |
| SIO.D1 | server to client | recovery off | The client loses each event from the fault to the new connection. The band of the count comes from the band of the reconnect. No event comes twice. |
| SIO.D2 | server to client | recovery on, 30 s | The client gets each event once. `socket.recovered` is true on the new connection. |
| SIO.D3 | server to client | recovery on, 10 s, no event in the 70 s before the fault | The session is alive at the new connection, but the timer removed the last event. Thus `socket.recovered` is false. |
| SIO.D4 | server to client | recovery on, 2 s | The session expires before the new connection. Thus `socket.recovered` is false. |
| SIO.U1 | client to server | no retries | The server loses each event from the fault to the expiry of the ping of the client. The server gets each later event after the reconnect, once. |
| SIO.U2 | client to server | retries, one event in flight | The event survives when its failed tries before the reconnect are at most `retries`. Each ack timeout is one try, and the disconnect is one more. |
| SIO.U3 | client to server | the settings of SIO.U2, with one retry less | The last failed try is past `retries`, thus the client drops the event. The server does not get it. |

The naive claim of SIO.D3 is that a drop shorter than the limit recovers. The window of 70 s puts at least one firing of the timer after the last event is 10 s old. The naive claim of SIO.U2 and SIO.U3 is that `retries` counts losses of the event. The source counts the time of the outage in ack timeouts.

**The edges.** The count of failed tries in SIO.U2 is 1 plus the ack timeouts before the detection. The cells choose the ack timeout so that no timeout lands inside the band of the detection timer. The same rule keeps the moves of SYS-77 away from a firing.

**The harness.** The cells need two changes of the harness:

1. A stream mode of the WebSocket probe. One side sends the numbered events, and the other side writes one line for each event.
2. A measure of a pair of programs: the count of the lost events, the count of the repeated events and the value of `recovered`. The bands are the bands `lost` and `duplicates` of a group prediction, on a cell with one pair.

A third cell type tests repeats: a stall in one direction, where each try arrives and each ack dies. The server then counts each try past the first as a repeat. The harness has no stall in one direction, thus this cell waits for that fault.

**The prediction.** The bands go to the record of predictions before the first dispatch, as in the first slice of SYS-77.
